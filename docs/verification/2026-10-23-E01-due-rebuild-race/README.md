# E01 到点重建与闹钟并发交付

- 日期：2026-10-23；设备：专用 `PJ_API36_16K` 模拟器，API36/16KiB。
- 背景：冷进程闹钟修复后，用户恰在提醒到点时打开应用，`MainActivity` 启动的重建仍可能与闹钟接收器并行。旧逻辑先取消旧 Alarm、增加 generation，导致已到点事件不再投递。
- 实现：`ReminderScheduler` 用同一互斥锁串行化重建与闹钟投递。重建在取消旧 Alarm 前投递最近 15 分钟内、属于原调度集合的到点事件；`ReminderStore` 持久记录已投递的事件键与触发时间，避免晚到旧回调重复通知。已有通知在重建后更新动作代际且只更新、不再次提醒；用户清除通知后不会重新弹出。恢复替换会清除投递账本。
- 定向设备测试覆盖两种顺序：重建先、旧闹钟后；闹钟先、重建后。两种都检查实际系统活动通知、去重和用户清除后的行为。[提醒调度/通知/页面回归](reminder-regression.log) **11/11 通过**。JVM **340/340**，最终 lint **0 错误/36 警告**。
- 首轮 [API36 全量](api36-full.log)执行 **319 项/9 失败**，失败全部集中在 `UiSnapshotTest`：其合成记录固定“今天 09:30”，夜间运行时属于未来时间，业务校验正确拒绝。修正截图夹具为“同日、不晚于当前时刻”的时间后，[截图类定向复测](snapshot-rerun.log) **9/9 通过**。[全量重跑](api36-full-rerun.log)最终 **319 项执行、272 通过、47 前置条件跳过、0 失败**；两项新增并发测试在全量内均为通过。精确闹钟 app-op 保持 `default`。
- 边界：两种并发顺序通过可控设备测试覆盖，用户恰好同毫秒打开应用的实际时序、长期待机与小米/OEM 后台策略尚未实测。47 项跳过需按原各项前置条件解释，不能折算为通过。
