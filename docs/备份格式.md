# 备份与数据格式

日期：2026-11-12。对应源码 0.26.0-dev / versionCode27 / schema15。
本文描述**已实现**的字节格式与认证范围。凡未由测试直接覆盖的项目，在文末“未验证边界”列出，不作保证。

## 1. 密钥与派生

- 设备根密钥（VMK）：256 位，由 Android Keystore 保护，永不落盘明文。
- 派生：Tink HKDF-SHA-256，以资料库 ID 为盐、用途字符串为上下文，派生数据库、对象、清单、提交、恢复设置、代际封装等相互独立的密钥。
- 恢复密钥：随机 256 位，文本形式 `YJ1:` + Base64URL（32 字节原文 + SHA-256 前 4 字节校验）。与云盘应用密码无关。

## 2. 通用密文信封

`VaultCrypto` 外层（用于清单、提交、恢复设置、代际封装等小对象）：

```
PJE\x01 | 12 字节随机 nonce | AES-256-GCM 密文与 128 位 tag
```

AAD 绑定用途与身份，例如清单为 `backup/v1/<vaultId>/manifest`、提交为 `cloud-commit/v1/<vaultId>/<snapshotId>`、代际封装为 `generation-key/v1/<deviceVaultId>/<generationId>`。AAD 不匹配即认证失败。

附件对象（`PJF1`，支持有界内存流式处理）：

```
PJF\x01 | 12 字节随机 nonce | AES-256-GCM 密文与 128 位 tag
```

对象路径为随机 UUID + `.bin`，不含原始文件名。原件上限 100 MiB；写入采用流式加密 + 刷盘 + 重命名，失败删除暂存文件。

## 3. 本地加密备份 `.yunji`

ZIP 容器，条目固定为三类：

| 条目 | 内容 |
|---|---|
| `vault.json` | `RecoverySlot`：`YJ-RECOVERY-1` 封装（`HKDF-SHA256-AES256-GCM` + Base64URL 包裹的主密钥），公开可读但不含恢复密钥 |
| `manifest.enc` | `PJE1` 加密的业务清单（下节） |
| `objects/<uuid>.bin` | 已加密原件与缩略图密文，逐项校验长度与 SHA-256 |

限制：条目数 ≤ 200002、总密文 ≤ 8 GiB、单个清单 ≤ 16 MiB；ZIP 预检拒绝路径穿越、重复条目、不支持的路径名与压缩炸弹。

## 4. 业务清单（加密）

`manifest.enc` 解密后为 UTF-8 JSON，含 `formatVersion`、`schemaVersion`、`vaultId`、`snapshotId`、`writerId`、`writerSequence`、`capturedSequence`、`createdAt` 与 13 类业务表数据；附件以对象引用 + 原文/密文长度与 SHA-256 表示。解码时校验资料库身份、嵌套深度（≤32）、关联关系与内容约束。**不含**未提交草稿、导入来源 URI、云盘凭据、恢复密钥、设备封装与本机设置。

## 5. 云端目录与提交

云端路径：`<所选目录>/pregnancy-journal/<vaultId>/`，内含 `vault.json`（身份与恢复封装）、`objects/`、`snapshots/`、`commits/`。

- 快照：`snapshots/<snapshotId>.bin`，即上述清单密文。
- 提交：`commits/<snapshotId>.json`，`YJ-COMMIT-1` 信封：

```json
{"format":"YJ-COMMIT-1","snapshotId":"<uuid>","cipherSize":<int>,"cipherSha256":"<hex64>","authenticated":"<base64url>"}
```

`authenticated` 为 `cloud-commit/v1/<vaultId>/<snapshotId>` 为 AAD 的 PJE1 密文，其明文为 `{vaultId, snapshotId, writerId, writerSequence, capturedSequence, createdAt, cipherSize, cipherSha256}`。因此提交不仅绑定清单哈希，也绑定写入者与序号；文件名与信封 `snapshotId` 不一致即拒绝，复制到别的文件名不构成新快照。

上传顺序：目录与身份检查 → 逐对象“先回读校验、缺失才上传、已存在但损坏则停止且不覆盖” → 上传清单并回读校验 → 发布提交 → **回读提交并验证认证与引用**，通过后才记录成功。

## 6. 代际（generation）与切换

- 布局：旧安装沿用 `vault/journal.db`；新代际为 `vault/gen/<uuid>/journal.db`，且**每个代际拥有自己的 `objects` 目录**（不同 VMK 下密文不可混用）。
- 指针：`vault/active-generation.json`，只含随机 UUID；先写临时文件并 fsync，再原子替换并同步目录。
- 代际密钥封装：`material.enc`，`PJE1` 包裹恢复后资料库的 VMK，AAD 绑定设备资料库与代际；拒绝覆盖已有封装。
- 恢复日志：`restore-journal.json`，阶段 `PREPARED → SWITCHED → VERIFIED`。启动时：未切换则丢弃暂存；已切换但新库不可用则回滚上一代际或旧布局；回滚后关闭日志。

## 7. 版本兼容

- schema：当前 13，1→13 全部为自动迁移，迁移测试覆盖已发布路径。
- 清单/提交/信封：格式字段不匹配即拒绝；**高于当前支持版本时提示升级，不尝试降级导入**。
- 应用降级不等于数据格式降级：旧 APK 无法读取新 schema 时不得强行回退，应通过兼容版本恢复升级前备份。

## 8. 未验证边界

- 真实云盘服务商的 DELETE/`getlastmodified` 行为、配额与限流组合未联测。
- 跨设备并发（双 writer）与网络分区只按 writer 分支保全快照，未做强制排他验证。
- 物理断电、真机进程终止、OEM 后台限制下的切换与清理未验证。
- 大包（数百 MiB 原件）低内存矩阵与 16 KiB 页已做静态与运行时检查（见测试验收报告），但未在低内存真机复测。
